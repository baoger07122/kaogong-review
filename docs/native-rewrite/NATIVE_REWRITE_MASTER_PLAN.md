## 1. 验收规则

每个功能必须经过三个层级，不能只凭“页面已经写出来”判定完成：

| 状态 | 含义 |
| --- | --- |
| ✅ | 已完成或已经验收通过 |
| ⬜ | 尚未开发、尚未构建或等待用户确认 |
| ⚠️ | 功能可运行但发现问题，必须修复并重新验收 |
| — | 纯内部工程项目，不需要用户在 iPad 上检查 |

三列责任分别为：开发由 Codex 完成，构建由 Codex/CI 验证，用户栏由用户在 iPad 真机验收。

### 1.1 预览确认与正式验收的对应关系

| 确认层级 | 用户如何确认 | 确认后动作 | 是否还需 IPA 重复确认 |
| --- | --- | --- | --- |
| 设计图 | 回复选择的方案 | 制作 Swift Playgrounds 真实预览 | 需要继续看真实预览 |
| Playgrounds 预览 | 明确回复“确定预览” | 立即迁移到 `native-ios/**` 并接入正式数据/路由 | 页面结构、视觉和基础点击不重复确认 |
| 正式构建 | Codex 编译和自动检查通过 | 勾选开发/构建，准备阶段交付 | 数据和系统能力仍可能需要 IPA |
| 真机 IPA | 用户安装并检查指定项目 | 勾选用户验收或登记问题 | 阶段最终确认 |

“确定预览”只确认预览实际展示过的部分。模拟数据无法证明持久化和统计正确，Playgrounds 也无法完全证明震动、键盘、文件、前后台、性能和真机系统动画，因此这些项目不能提前标记为用户验收通过。

阶段完成必须同时满足：

- ⬜ 本阶段所有必做项的“开发”和“构建”均已勾选。
- ⬜ 已生成对应版本的未签名 IPA，并保存到 `downloads/native/版本号/`。
- ⬜ 已提供本阶段变更说明、已知风险和测试步骤。
- ⬜ 用户已逐项检查，关键项的“用户”栏均已勾选。
- ⬜ 用户明确回复本阶段通过，才能进入下一阶段的正式签收。

状态约定：`未开始`、`开发中`、`待真机验收`、`有问题`、`已通过`。用户验收发现问题时，不删除原条目，在“问题记录”中登记并重新生成 IPA。

## 14. 每阶段固定交付内容

每一阶段结束时，Codex 必须提供：

- ⬜ 阶段版本号和 Git 提交。
- ⬜ 工作区内可点击的未签名 IPA 文件。
- ⬜ 已完成清单和仍未完成清单。
- ⬜ 与 Web 基线相比的功能差异。
- ⬜ 数据结构和迁移影响。
- ⬜ 已知风险与回滚方法。
- ⬜ 面向用户的逐步测试说明。
- ⬜ 本文档对应条目的状态更新。

任何功能只有“开发完成”但没有经过用户真机确认时，统一称为“待真机验收”，不得称为“全部完成”。
