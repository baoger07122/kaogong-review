## 原生版本号规则

- 格式：`月.日.当天原生迭代次数`，例如 `8.26.4`。
- 原生版本独立计数，不与仍在维护的 Web 版本共用当天次数。
- 同一天每生成一个新的可测试原生 IPA，末位递增一次。
- 跨天后的第一个原生 IPA 从 `.1` 开始。
- 修改 `native-ios/**` 后必须同步修改 `MARKETING_VERSION`、构建号和设置页展示版本。
- 构建失败且没有发布 IPA时可沿用该版本号继续修复；一旦 IPA 已发布，后续原生代码修改必须使用新版本。
- 纯文档、验收记录和说明文字修改不升级 App 版本，也不重复构建 IPA。
- 云端构建按 `Asia/Shanghai` 日期自动校验版本号，防止漏改或沿用已经发布的版本。

## iPad 设计预览与截图验收规则

原生 UI 不采用“改一次样式、安装一次 IPA”的低效流程。视觉调整统一分为三层：

1. **设计图确认**：先输出候选布局图片，只确认结构、密度、尺寸、颜色和选中状态；不修改正式 App 代码，不升级版本。
2. **SwiftUI 真实截图确认**：设计通过后实现代码，由 macOS/Xcode 使用 iPad 模拟器或固定 SwiftUI 视口输出截图；这张图代表真实代码渲染，不需要安装 IPA。
3. **真机 IPA 验收**：模拟器截图通过后才生成 IPA，真机重点验证动画手感、震动、键盘、安全区、分屏、旋转、Apple Pencil、性能和数据保存。

每个主要页面至少检查以下视口：

- iPad 横屏全屏。
- iPad 横屏约半屏宽度（主要使用场景）。
- 半屏宽度附近的较窄和较宽边界，防止拖动分屏分隔线时布局突然错乱。

实现要求：

- 使用 SwiftUI 自适应布局和尺寸断点，不按截图像素硬编码页面。
- 设计稿和实现截图使用同一组点尺寸、字体层级、安全区和内容数据。
- 模拟器型号应尽量与用户实际 iPad 型号一致；实际型号未确认前，半屏截图只作为基准预览，不能冒充真机精确尺寸。
- 每轮截图明确标注设备型号、方向、视口宽高、系统版本、页面状态和对应 Git 提交。
- 视觉差异在截图阶段返工；只有截图确认后才发布新的测试 IPA。

### “确定预览”后的正式开发规则

用户明确回复“确定预览”时，表示当前预览的页面结构、视觉层级、尺寸密度、图标和基础点击路径已经通过，不再等待 IPA 重复确认这些内容。Codex 必须立即执行：

1. 将该预览标记为 UI/交互基线并停止继续漂移设计。
2. 在同一阶段把已确认的 SwiftUI 视图迁移到 `native-ios/**`，不能让功能长期停留在 `native-preview/**`。
3. 尽量复用同一份视图结构，通过协议或依赖注入把模拟数据替换为 SwiftData/API 数据，避免重新照图写一套造成差异。
4. 正式迁移后完成编译、数据接入和路由检查，再勾选“开发”和“构建”；没有编译通过不能因为预览已确认而标记开发完成。
5. 如果正式 App 因系统限制必须改变已确认的布局或交互，必须先说明差异并重新提供预览，不能自行改动。

预览确认可以直接替代后续 IPA 中的重复视觉确认，但以下项目仍必须通过正式构建或 IPA 验证：

- SwiftData 持久化、备份导入、云 API、真实数量和数据安全。
- 原生震动、音效、通知、键盘、PencilKit、TextKit 和文件选择器。
- iPad 安全区、旋转、分屏边界、前后台恢复、性能和内存。
- Liquid Glass 等依赖真机渲染和动态手感的系统效果。

因此，新的开发节奏是：

`制作预览 → 用户回复“确定预览” → 立即迁移正式代码 → 编译与数据验证 → 阶段需要时生成 IPA 验证原生能力`。

### 全局 UI 设计系统与 UI 实验室

业务页面正式设计前，先在 Swift Playgrounds 的“设置”入口建立可交互 UI 实验室。后续页面不得各自重新定义相同控件，只能复用已确认的设计令牌和组件。

全局设计系统至少包括：

- 颜色：主色、成功、警告、危险、文字层级、页面背景、卡片背景和分隔线。
- 字体：页面标题、分区标题、卡片标题、正文、辅助文字、标签和大数字。
- 尺寸：页面边距、组件间距、圆角、点击区域、图标和控件高度。
- 容器：普通卡片、统计卡片、快捷入口、列表行、便签卡片和玻璃/材质使用边界。
- 操作：主按钮、次按钮、文字按钮、危险按钮、浮动新增按钮和按压反馈。
- 表单：输入框、文本域、日期选择、属性选择行、标签和分段选择器。
- 反馈：新增/编辑弹窗、删除确认、Toast、空状态、加载状态和错误状态。
- 动效：页面切换、选中切换、弹窗出现、保存成功和减少动态效果。
- 适配：iPad 横屏全屏、主要半屏和较窄分屏断点。

UI 实验室不是静态色板。用户必须可以实际点击按钮、输入文字、切换选择、打开新增弹窗、触发删除确认并查看空/加载/错误状态。所有操作使用内存模拟数据，不接触正式数据库。

UI 规范的确认口令同样是“确定预览”。确认后，设计令牌和公共组件立即迁移到 `native-ios/Sources/DesignSystem/`，后续页面必须复用；如需新增组件，先补充 UI 实验室并再次确认。

当前暂行 UI 组件基线已于 2026-08-27 由用户确认，并迁移到正式 `DesignSystem`。后续页面只能复用该基线；新组件或规则变化继续走预览确认流程。

### 统一交互库准入规则

- 页面不得自行新建弹窗、选择器、删除确认、Toast、手势或键盘交互；先检查统一交互库并复用已有组件。
- 新交互必须先登记到 `INTERACTION_LIBRARY.md`，在 Playgrounds UI 实验室提供可操作预览。
- 只有用户明确回复“确定预览”，该交互才能进入正式 `DesignSystem` 组件库并供业务页面使用。
- 已确认交互如需调整，必须重新预览确认，不能由单个页面静默改变全局行为。

原生 IPA 工作流只允许手动触发。正式原生代码可以持续提交，但只有阶段需要真机验收或用户明确要求生成 IPA 时，才更新版本号并启动构建。

## 不可变边界

1. 正式 iOS App 的页面和业务交互全部使用 SwiftUI/UIKit。
2. 不在正式 App 中嵌入现有 Web 页面或 Web 编辑器。
3. 涂鸦使用 PencilKit；富文本使用 TextKit/UIKit；速算使用 SwiftUI；思维导图使用 SwiftUI Canvas/Core Graphics。
4. Web `main` 独立运行，本分支不得修改、覆盖或强推 Web `main`。
5. 现有备份 JSON、记录字段和云端 API 必须保持可读兼容。
6. 未识别的旧字段必须原样保留，不能因为原生模型尚未使用就丢弃。
7. 每个阶段必须更新验收矩阵并生成可安装的未签名 IPA。
