## 1. 保留段落、行内样式和缩进

**入口与现象**　错题详情 → 错题笔记 → 点击编辑 → 完成 → 关闭并重开该题。编辑截图中的「设计方式」在句中加粗，保存后独占一行，后续正文另起一行。两个整段加粗的条目两侧也出现大段空白。用户同时反馈原有缩进丢失。截图能确认排版变化，无法确认新增的是存储里的段落标记，还是 HTML 导入恢复段落后的视觉效果，也无法据此恢复每一处原始缩进量。

**新增实机对照**　2025 江苏第 40 题，左侧从 ChatGPT 选中三条项目。右侧编辑态已插入三条完整正文，词头加粗，冒号和解释仍接在词头后面，但项目符号和续行缩进已看不到。右侧点完成后的展示态中，每条词头单独一行，冒号和解释移到下一段，三条之间新增大块留白。本例证实点完成即出现结构差异。原图选区从第一条词头开始，第一枚圆点可见于选区外；剪贴板是否携带列表语义仍需复现确认。本例三条文字在编辑态都可见，因此第 2 项的长内容显示问题仍用独立样例验证。[刚粘贴](C:/Users/bao/AppData/Local/Temp/codex-clipboard-232bb2b9-932c-4a62-8ad5-2b5efef1bcae.png) [点完成后](C:/Users/bao/AppData/Local/Temp/codex-clipboard-32a7ccc3-590f-4a44-864c-d8bdfecc0979.png)

**现有行为和原因**　`NativeRichTextEditor` 的 `changeIndent` 以 18 pt 步长修改 `firstLineHeadIndent` 与 `headIndent`。`noteHTML` 显式保存的段落属性只有字号和间距。`noteInlineHTML` 则按属性段逐次调用系统 HTML 导出，提取每段的 `<body>` 内容后直接套上 `strong` 等行内标签，可能保留系统为该片段生成的 `<p>` 等块级外壳。`wrappingInParagraphIfNeeded` 只检查拼接结果的开头。一个逻辑段因此可能导出成几个块，或出现行内标签包裹段落。局部加粗引发的额外段落与截图吻合。`LibraryInlineNoteSaveService.prepare` 直接保存收到的 HTML，未新增换行。`LibraryInlineNoteView.installConfirmedPreview` 优先复用同一版本的编辑快照，`prepareNote` 冷读时重新解析已存 HTML。解释保存前后为何可能看起来不同。对应导出逻辑在 `7ce13b8` 引入，11.14.1 中仍存在。尚未从该笔记原文核验具体生成了哪种标记。[HTML 段落规则](https://html.spec.whatwg.org/multipage/grouping-content.html#the-p-element) [UIKit 的段落属性](https://developer.apple.com/documentation/uikit/nsparagraphstyle)

**编码**　在 `NativeRichTextEditor.swift` 的 `noteHTML` 和 `noteInlineHTML` 修正错题笔记专用的导出路径。先确定逻辑段落，再按样式区间输出该段内容。各段只生成一层符合语义的正文、标题或现有列表块；引用容器包住属于同一段组的段落。一个句子里的普通文字、粗体、斜体、下划线、字号、颜色和链接都是该段内连续的行内节点，不得把 UIKit 导出的块级外壳带进这些节点。每一小段只编码实际文本及需要的行内属性，合并相邻同样式段，保留文字之间的空格。附件使用现有图片、表格与公式标记，保留位置、表格内部样式和附件内容。显式区分自然折行、段内软换行、Enter 分段、用户刻意留下的空段落。自然折行不写入换行字符；软换行写 `<br>`；空段由段落编码，还原时只产生一个对应的空行。保留段首实际输入的空白，包括全角空格、制表符和需要保留的连续半角空格。

**项目符号和续行缩进**　`preparedClipboardText` 可同时读到 RTF／RTFD 和 HTML，但目前 `finalizedRichPaste` 在选定富文本后，仅借 HTML 恢复部分标题和引用语义，未明确核对 `ul`／`ol`／`li` 边界或导入得到的 `NSParagraphStyle.textLists`。工具栏的项目符号又以字面前缀识别，`noteHTML` 的段落元数据未保存列表层级和标记。复现时分别检查剪贴板里的列表、富文本存储里的列表属性和已导出内容。HTML 带有列表结构，或 RTF／RTFD 已提供列表属性时，在贴入前保留或补回列表类型、顺序、层级和续行缩进。另一份剪贴板表示要先与所选正文可靠配对，才能补回结构。纯文本已有圆点、编号或可识别的 Markdown 列表时保留其含义。多种表示均无列表证据时，按普通正文贴入。每个项目只有一个标记，标记、词头、冒号和解释仍在同一列表项内，续行与正文起点左对齐；列表之间不得自动添加空段。保留现有字号和笔记样式。语义列表与工具栏生成的字面前缀统一交给同一导出和恢复路径，一项只保存一次，避免重复圆点。旧存储可安全读回，缺失标记只有在结构仍在时才恢复。[UIKit 列表段落属性](https://developer.apple.com/documentation/uikit/nsparagraphstyle/textlists)

**缩进与读回**　在 `NativeRichTextNoteParagraphHTMLPolicy` 明确持久化 `firstLineHeadIndent`、`headIndent` 和原本存在的 `tailIndent`，按 pt 保留，使用可读的 HTML 样式和能在导入端可靠配对的段落元数据。首行相对普通行的偏移只能应用一次。正常导入明确映射到对应 `NSParagraphStyle` 属性，避免依赖系统 HTML 导入器隐式推断；引用沿用 12 pt 默认缩进和左侧引用线，手动增加或减少的缩进应和编辑态一致。安全回退若支持这些信息，应用同样的段落边界和缩进。无法无损恢复的内容保留原始 HTML、附件和现有只读保护。用同样的内容宽度和段落参数比较编辑、点击完成和重开三个阶段。保留 16 pt 默认正文和 11.12.4 间距规则，保留已有合法段落样式。按现有版本校验和草稿流程保存，不能用缓存掩盖冷读问题。

**旧笔记**　先按有效原文重建排版。对含旧导出器生成的异常块结构，有足够证据确认属于同一逻辑段时在读回时合并，保留样式边界和原始存储；找不到原段落边界或缩进值时保留原文，禁止全局删除空行或凭内容猜测缩进。进入详情、切换编辑或读取旧笔记不自动改写数据库。用户实际修改并成功保存后才写入新的格式。

**验收**　用真实编辑和冷读路径验证，现有行为检查补上能捕捉属性段误拆分的用例。在同一段输入「建筑脱离现实生活的设计方式，与文段更贴合」，只选中「设计方式」加粗；在另一段用一次缩进（18 pt），写到自然折行，再加一段 12 pt 默认引用、一次软换行和一个手动空段。输入时、点完成、退出详情重开、杀进程重开后，比较段落数、行内属性范围、缩进值和视觉断行，等宽时位置一致。检查全段加粗项前后没有额外空行，用户手动留的空段仍在，缩进连续加减可重复保存。再覆盖 ChatGPT 粘贴内容、图片和表格、原样健康旧笔记、能可靠修复的异常旧结构及无修改打开。根据原应用入口在 iPad 验收，检查原文或脱敏复现样本中的 HTML 结构及重新解码后的属性。源码和编码检查通过仅可报告对应结果。

**截图回归**　使用「比比皆是」「巍然挺立」「整齐划一、秩序井然」三条作等宽对照。用带结构的无序列表复制，分别比较整组复制和从首词开始框选。刚粘贴、自动保存仍在编辑态、点完成和退出重开时均须是三项；每项最多一个圆点，词头加粗，冒号及解释紧接，续行对齐正文。原文没有手动空段时不得出现图 2 的大片留白。另验纯文本缺失标记时只保留三个段落，不猜测项目符号；有序列表、嵌套列表、重复保存和在含表格的整段复制中均覆盖。

## 2. 长段粘贴后应能直接滚动看到全文

**入口与现象**　错题详情 → 错题笔记 → 编辑 → 粘贴长段内容。用户反馈最初只显示前几句，删除前文后才显示后文。后文能在删除后出现，优先检查编辑区测高和可滚动范围。本条缺少原始剪贴板和复现录屏，未验证不可见段落是否全部已插入，也未确认保存重开是否同样发生。

**现有行为和可能触发点**　`RichTextTextView.Coordinator.handlePaste` 在剪贴板导入及段距整理后调用 `replaceAttributed`。`NativeRichTextPastePolicy.replace` 直接把选中的富文本内容写入 `textStorage`，此处没有按几句截断的规则。`replaceAttributed` 的成功回调更新选区和安排发布，但未显式标记测高缓存过期。`scheduleLayoutAndToolbarRefresh` 在错题笔记里只在 TextKit 上报的高度通过校验且与旧值不同后，才通知 SwiftUI 重新测量。`contentHeight` 也可能依宽度复用旧高度或接收尚未覆盖文末的 `usageBoundsForTextContainer`。错题笔记的 `UITextView` 关闭内部滚动，外层详情由测量高度决定滚动范围。估算高度过短时后续段落无法通过正常滚动进入视野。删除文字会走 `textViewDidChange`，该回调另有明确的缓存刷新标记，与反馈的行为一致。该路径是源码里最直接的排查点，实机因果仍需复现。[Apple 的 TextKit 2 可视区域布局说明](https://developer.apple.com/videos/play/wwdc2021/10061/?time=342)

**输入与测量**　在 `NativeRichTextEditor.swift` 的 `replaceAttributed` 成功回调中，对当前文档会话与现有测量宽度显式做一次高度失效，涵盖粘贴、撤销与重做。合并同一轮重复通知。错题笔记在文档长度明显变化、替换结构内容或布局附件变动时，用当前文本容器宽度执行一次能覆盖最新正文末尾的重测，测量结果按文档会话、布局修订、宽度缓存。视图区估算不能覆盖新修订的可靠文末高度时，不用它清除测量失效标记。重测限于真实内容和窗口宽度变化；保留普通逐键、光标移动和中文输入组字的合并策略，禁止在每次转场或按键时强制全量布局。完成重测后外层详情可正常滚到文末，光标仍在本次插入区之后，键盘和格式栏不遮住光标。保留现有编辑区最小高度、字体、缩进、当前滚动位置以及撤销语义。

**核查数据与保存**　用脱敏样本比较粘贴源表示、实际插入范围、存储快照和冷读后的正文，日志仅记录长度、修订、边界与测量值。优先确认实际插入的尾段存在。若粘贴表示进入编辑器前已缺尾，按复现样本修正该导入分支，优先使用能完整保留正文和富文本的表示；确实只能取得完整纯文本时明确提示格式降级，保留原编辑内容与撤销能力。已有大文档安全预览须明确提示是否截断，原文留存，预览不得写回覆盖。与第 1 项共同验证自动保存和点「完成」使用同一份完整文档，保留内容顺序、用户空行、加粗、引用、图片和表格。

**验收**　准备 20 段带编号的文本，首尾使用不同短句，在空笔记和已有笔记中间粘贴，分别测试纯文本和 ChatGPT 富文本，另测有图片或表格的文档。粘贴后直接向下滚动看到最后一段，禁止删除前文作为显示步骤。确认文末可点选定位，键盘显示和隐藏时均能看到光标与末尾，验证覆盖选区、完整撤销和重做、窄窗口与横竖切换。点完成并关闭详情重开，检查首尾、编号、格式及附件相同。使用分段耗时和更新次数验证贴入后测高确有刷新，并确认普通逐键输入和光标操作未退回逐次全量测量。

## 3. 粘贴当下就应用错题笔记的排版

**入口与已确认的差异**　错题详情 → 错题笔记 → 粘贴。用户反馈刚粘贴时行距太紧，点「完成」后才出现预期间距。`RichTextTextView.Coordinator.handlePaste` 在导入和笔记段落整理之后，又调用通用 `NativeRichTextPastePolicy.compactParagraphSpacing`。这一步将超过 4 pt 的段前、段后距压到 4 pt，包含刚被笔记规则设为至少 5 pt 的引用段后距。`LibraryInlineNoteView.installConfirmedPreview` 对保存预览再次应用笔记段落规则，会恢复引用段后距。普通正文也存在路径差异：`normalizePastedFonts` 统一字号，`compactParagraphSpacing` 不管段内行高约束；`applyingNoteParagraphFormatting` 复制导入的段落样式，未明确归一来源的固定行高，因此可将与 16 pt 字体不一致的行高带进编辑态。保存后的 HTML 导入及第 1 项的段落编码差异也可能改变间距。当前没有同一次粘贴的剪贴板表示和段落属性，未确认普通正文是源行高、段落边界、测高或它们共同造成。

**样式规则及执行顺序**　保留已确认的 11.12.4 基准。错题笔记普通段正文 16 pt 系统字体，自然折行与段内软换行用此字号的系统自然行高，默认附加行距、段前和段后均为 0 pt；续行无需新增空段。用户真实空段保持一行。普通富文本复制带来的显式段前后距各上限 4 pt；无值回到普通默认值。粘贴来源的固定 `minimumLineHeight`、`maximumLineHeight`、`lineHeightMultiple` 在普通正文中用笔记默认值，防止字高被压；保留笔记里用户已有的有效显式布局。引用应用本 App 的 12 pt 缩进、浅灰竖线和 5 pt 默认段后距，再有其他缩进按第 1 项保留。标题沿现有字号和语义。上述步骤在剪贴板表示解码、来源普通段距整理之后，写入 `textStorage` 之前一次完成。通用粘贴规则照常供其他页面使用；外来段距的 4 pt 上限不得覆盖本地引用样式。现有笔记只改粘贴影响的范围；段内粘贴保持目标段落样式，独立插入的段落按上述规则处理。不改选区之外的格式。表格内部行距、图片、链接、加粗、缩进和正常手动换行照原样保留。

**保存与验收**　可信编辑快照、点完成即看、退出重开和草稿恢复共用同一套段落语义，落盘及反解按第 1 项保真。已规范化的文档重读时不重复压缩或补间距。测高按第 2 项执行。用相同宽度对比粘贴当下、点完成和重开后的布局。准备含一个自然折行长段、一个 `<br>`、两个非空段、一个手动空段、加粗及带来源显式段距的引用的样例。分别使用纯文本、HTML、RTF 和实际 ChatGPT 复制；含窄固定行高的 HTML 用作专项样例。检查段落属性、视觉间距和文末可见性一致，引用段距保持 5 pt，正文无额外空行。同样验证插入现有段落中间、撤销重做及表格前后。记录段距、行高和来源格式，不记录用户正文。

## 4. 核查词语编辑弹层顶部文字重叠

**入口与现象**　截图源为 149 × 210 px。放大能看见圆圈内的文字与弹层标题区域重叠，标题文案无法可靠辨认。画面有原生返回和右侧保存外观，推测是错题详情 → 选择关联 → 新建词语。`LibraryRecordDetailView.detailSheets` 以 sheet 内的 `NavigationStack` 打开词语编辑器。`LibraryRecordEditorView.configuredEditor` 明确显示导航栏，使用 `ScrollView` 和原生标题及保存动作，未显式指定词语编辑页的导航栏背景持续可见。系统滚动边缘外观是候选原因，需在匹配入口确认有正文进入标题区域后再落实该调整。[截图](C:/Users/bao/AppData/Local/Temp/codex-clipboard-db9883c6-c9c7-4983-b7d1-bb62eb967e54.jpg) [Apple 的导航栏背景可见性](https://developer.apple.com/documentation/swiftui/view/toolbarbackgroundvisibility%28_%3Afor%3A%29)

**实现与验收**　若复现为词语编辑页正文透过顶栏，修复仅限定在该词语编辑页。顶部继续使用系统导航栏，标题居中，左返回，右保存；为导航栏使用与现有白色表单一致的纯白不透明背景并保持可见。滚动内容从导航栏底部以下呈现，保留系统安全区和弹层现有圆角。检查是否有滚动内容因布局或手动位移进入标题点击区域，按实测修正该区域的内容边界，不加硬编码的导航栏高度。用错题关联新建和词语库新增／编辑两条入口，输入带表格的长内容，上下滚动、弹出键盘并切换横竖及窄窗口。标题、返回和保存始终清晰可点，正文不穿过标题，按现有规则保存。若实际圈选的不是该界面，按实机确认的具体入口更新本条后再动对应界面。
